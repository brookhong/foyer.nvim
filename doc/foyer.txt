1. INTRODUCTION                                           *foyer-introduction*

*foyer.nvim* puts a normal, modifiable buffer in front of a |terminal| buffer.
You compose a command with the full power of Vim, press <CR>, and the text is
sent to the shell.

A foyer is the room you pass through on the way in. Nothing reaches the shell
until you are done with it here.

It also manages named, project-scoped terminals, keeps a persistent per
terminal command history, and can edit a visual selection in a scratch window.

The plugin defines no global mappings. See |foyer-api| and wire up the
functions you want.

==============================================================================
2. REQUIREMENTS                                           *foyer-requirements*

Neovim 0.10 or newer. No other dependencies.

3. SETUP                                                         *foyer-setup*

                                                               *foyer.setup()*
setup({opts})

{opts} is a table with the following keys. All are optional.

commands ~
    Table of terminals, keyed by the single character that selects them in
    |foyer.terminal_command()|. Each value is one of:

    - a string: the command to run, e.g. `'zsh'`
    - a table `{ command, arguments }`; the first element doubles as the
      display name in the window title
    - a function `f(project_root, launch_info)` returning either of the above.
      It is called every time, so the terminal can depend on the project.

    A table entry may also name, alongside its two elements:

    cwd     Directory the terminal is spawned in, instead of the project root.
    scope   `'global'` keeps one terminal for the whole session, wherever you
            are, and one context file with it. Anything else, or nothing, is
            the default: one terminal per project root. A global
            terminal's prompt takes the current window rather than a float
            or a sidebar, and the terminal takes it in turn once you send;
            closing either hands the window back to the buffer it showed.
            Use it for an agent you want a single long conversation with,
            apart from any project: >lua
        commands = {
            z = 'zsh',
            a = { 'opencode', '-c' },
            F = { 'opencode', '-c --agent counselor',
                  cwd = vim.env.HOME, scope = 'global' },
        }
<
root_markers ~
    List of directory markers used to locate the project root that scopes
    terminals, as accepted by |vim.fs.root()|. Defaults to
    `vim.g.root_markers`, then `{ '.git' }`.

bracketed_paste ~
    Whether a multi-line send is wrapped in bracketed paste, see
    |foyer-limitations|. Turn it off for a terminal program that does not
    understand the escapes. Defaults to `true`.

picker_delay ~
    Milliseconds |foyer.terminal_command()| waits for a terminal key before
    showing its picker. A key typed within it is taken with nothing drawn, so
    a mapping run straight through to the key does not flash the popup.
    Defaults to `500`.

selection_max_lines ~
    A selection is sent with its lines up to this many, and as its location
    alone beyond, see |foyer-opts|. `0` never sends the lines. Defaults to
    `40`.

mention ~
    Whether `@` in a terminal's prompt lists the open files to mention, see
    |foyer-mention|. Defaults to `true`.

                                                           *foyer.send_prefix*
send_prefix ~
    Keys that clear the receiver's input line and its screen, keyed by the
    program receiving them. Before the text, foyer clears whatever the
    receiver has on its input line, and clears the screen with it: CTRL-U then
    CTRL-L, or `{ ESC, '' }` for cmd.exe. Those are a shell's bindings, and a
    program with a UI of its own is free to bind them to anything -- `pi`
    erases the line on CTRL-U as a shell does, but opens its model picker on
    CTRL-L, which then swallows the prompt arriving behind it. So name the
    keys the program does understand, and `''` for the rest: >lua
        send_prefix = {
            -- { clear input, clear screen }
            pi = { vim.keycode('<C-u>'), '' },
            claude = { '', '' },
        }
<
    A send is prefixed with both, the input key first. The input key alone is
    also what |foyer.edit_input()| sends to find the command line, so a
    program given `''` there leaves it nothing to read -- reading back a
    prompt is a shell feature either way.

    The key names the program, not the `commands` key that selected it: one
    such key stands for whatever a project wants behind it, so `a` is free to
    be a different agent in every repo. The whole command line as spawned, the
    program alone and its basename are all tried, so `pi --yolo`,
    `/opt/pi/bin/pi` and `pi` are all usable keys -- the basename covers every
    path and argument spelling at once. A program with no key of its own keeps
    the defaults.

Example: >lua
    require('foyer').setup({
        commands = {
            z = 'zsh',
            g = 'gdb',
            a = { 'opencode', '-c' },
        },
    })
<
                                                                  *foyer-opts*
                                                           *foyer.launch_info*
launch_info ~
    The context a prompt was composed with. |foyer.terminal_command()| and
    |foyer.send_terminal_command()| capture it
    themselves, so a mapping does no bookkeeping. Passing one explicitly
    overrides the capture. It reaches the `commands` resolver
    untouched -- the plugin never inspects it -- and is published per terminal
    for an agent to read later, see |foyer-context|. The shape is: >lua
        {
            project_root = '/repo',
            current_file = 'src/main.c',   -- relative to project_root
            current_line = 88,
            start_line = 30,  -- visual mode only, the lower line number
            end_line = 36,    -- visual mode only, the higher line number
        }
<
    `current_file` is named the way the project names it, not the way your
    filesystem does. The two keys always travel together: when there is no
    |foyer-setup| root to name the file against, `project_root` is absent and
    `current_file` is absolute instead.

    Any other key you add travels with it, all the way to the agent.

Command {opts} accepted by |foyer.terminal_command()| and
|foyer.send_terminal_command()|:

    command       Send this text instead of opening a command buffer.
    interactive   Force the command buffer open even when `command` is set;
                  `command` then seeds the buffer.
    selection     Text appended to the prompt as it is sent. Set for you
                  when the send starts in Visual mode. See below.
    win_type      `'sidebar'` for a right-hand split; otherwise floating.
                  Ignored for a `scope = 'global'` terminal, see
                  |foyer-setup|.
    auto_start    Spawn the terminal if it does not exist yet.
    launch_info   See |foyer.launch_info|.

|foyer.terminal_command()| also accepts:

    key           The `commands` key to drive, instead of asking for one.
    switch        Show the terminal in the current window rather than opening
                  a prompt for it, and return its buffer.

Starting from Visual mode attaches the selection. The command buffer opens
empty and in Insert mode, with the selection's place shown in its title --
`src/main.c:30-36` -- and the selection joins below the prompt, after a blank
line, as it is sent: >
    what does this do?

    Selected in my editor: /repo/src/main.c, lines 30-36
    ```c
    ...the selected lines, as the buffer has them...
    ```
<
The lines go with it because a bare `src/main.c:30` reads to an agent as a
location, and it reads the lines around one and guesses which was meant; and
the numbers are the buffer's, while the agent reads the file on disk, which
unsaved edits can put out of step -- the label says so when they have. The
path is absolute, so it resolves wherever the agent was started. A selection
longer than `selection_max_lines` is sent as the label alone.

None of it sits in the command buffer, so the line stays yours to edit and to
walk history with, and history remembers the prompt without a selection that
will not be true next time. Type nothing and nothing is sent; a selection
alone asks the agent nothing. A `selection` you pass yourself is appended as
given.

A sidebar outlives the send that opened it, so sending again aims at the
window already there rather than splitting another one: a draft still in it is
yours and stays -- only an empty one takes a seeded `command` -- with the new
selection replacing whatever the title advertised before, and the terminal
left in there by the last send gives the window back to a fresh prompt. A
floating window is transient and is simply opened again.

A terminal still producing output keeps the window instead, see
|foyer.is_idle()|; there is no prompt for a selection to ride on then, so it
is dropped and said so via |vim.notify()|.

4. API                                                             *foyer-api*

                                                    *foyer.terminal_command()*
terminal_command({opts})
    Wait for a `commands` key, spawn that terminal if it is not running for
    the current project root, then open a command buffer for it. With no key
    typed within `picker_delay`, a popup lists the keys, tagging global
    terminals `global` and gathering them at the bottom, and marking running
    ones `●`. <Esc> or CTRL-C cancels; a key that names no terminal is
    ignored, and one typed before the popup showed brings it up.

    `opts.key` names the terminal outright, so a mapping can go straight to
    one, and `opts.switch` steps into its buffer instead of opening a prompt.
    A `scope = 'global'` terminal opens its prompt in the current window: >lua
        vim.keymap.set({ 'n', 'v' }, '<leader>af', function()
            foyer.terminal_command({ key = 'F' })
        end, { desc = 'opencode terminal' })
<
    The context is published on every call, switch or spawn, so an agent
    already running in there learns where you are now.

                                               *foyer.send_terminal_command()*
send_terminal_command({term_key}, {opts})
    Drive a specific terminal without prompting for a character. With
    `opts.command` set, the text is sent non-interactively; otherwise a
    command buffer opens. With `opts.auto_start` the terminal is created if it
    is missing.

                                                          *foyer.edit_input()*
edit_input()
    Lift the terminal's current, half-typed command line into a floating
    buffer and write the edited result back to the prompt. Must be called from
    a terminal buffer, in Normal mode.

                                                      *foyer.edit_selection()*
edit_selection()
    Open the current visual selection in a floating buffer and replace the
    selection with the result. Must be called from Visual mode. Uses register
    a as the transport.

                                                    *foyer.toggle_full_size()*
toggle_full_size()
    Toggle the current window between full screen and the size it had before:
    height for a float, width for a split. The size is remembered per window,
    so two windows toggle independently. Full screen is a request, not a
    promise: a neighbouring split keeps its minimum width, so a split may stop
    a few columns short of 'columns'.

                                                          *foyer.tab_switch()*
tab_switch()
    Move to the next window worth looking at: CTRL-W w order, wrapping around,
    skipping floats and any window a full-screen neighbour has squeezed down to
    'winminwidth' or 'winminheight'. With one window on top and two below whose
    left pane is squeezed, the right-hand pane therefore switches to the top
    window.

    When nothing is left to step into, the window stays put and the buffer
    changes instead, like CTRL-^. That happens when the tab page holds no other
    window — a float over it is not a destination — and when every other window
    is squeezed flat.

    A diff is the exception: a diff pane maximised with
    |foyer.toggle_full_size()| gives the squeezed pane its size back and steps
    into it, because a diff only reads beside its other half.

                                                              *foyer.is_idle()*
is_idle({buf}, {threshold_ms})
    Return true when {buf} has produced no output for {threshold_ms}
    milliseconds (default 1000). Used internally to decide whether a terminal
    is still busy, in which case the terminal is shown instead of a new
    command buffer.

5. AGENT CONTEXT                                               *foyer-context*

On every send, the |foyer.launch_info| attached to it is written as JSON to a
file per terminal, and every terminal this plugin spawns has $FOYER_CONTEXT in
its environment naming that file: >console

    $ cat "$FOYER_CONTEXT"
    {"captured_at":"2026-09-22T15:59:07+0800","captured_unix":1790063947,
     "launch_info":{"project_root":"/repo","current_file":"src/main.c",
                    "current_line":88,"start_line":30,"end_line":36}}
<
That is the whole interface -- a file an agent reads when it needs it. What
remains is telling the agent it is there.

`skills/foyer-editor-context/SKILL.md` in this repository does that as an
agent skill: only its one-line description sits in the model's context, and
the body is loaded on demand, when a request actually points at the editor.
Symlink it into whichever skill directory your CLI scans --
`~/.config/opencode/skills/`, `~/.kiro/skills/`, `~/.claude/skills/` --
keeping the directory name: >

    mkdir -p ~/.config/opencode/skills/foyer-editor-context
    ln -sf /path/to/foyer.nvim/skills/foyer-editor-context/SKILL.md \
        ~/.config/opencode/skills/foyer-editor-context/SKILL.md
<
A CLI with no skill mechanism can carry the same thing as an always-loaded
rule (`AGENTS.md`, `CLAUDE.md`, `~/.kiro/steering/*.md`), at the cost of those
tokens on every request: >

    When $FOYER_CONTEXT is set it names a JSON file holding the file, line
    and selection the user had when they wrote their prompt. Read it with
    `cat "$FOYER_CONTEXT"` before acting on "this file", "here", "this line"
    or "my selection". If it is unset, ask which file is meant.
<
Each terminal has its own file, so an agent in one project never reads a path
attached for another -- a `scope = 'global'` terminal has one file for the
session instead, since it is the same conversation everywhere. A terminal
opened by hand has neither the variable nor a send to trigger a publish, and
its agent has nothing to read.

The files live in `stdpath('cache')/foyer/`, one per terminal, and are removed
on |VimLeavePre|. A terminal closed and reopened keeps its file, so a long
session does not litter the directory.

Publishing never takes a send down with it. A `launch_info` holding something
|vim.json.encode()| refuses, or a cache directory that cannot be written,
warns and the command is sent anyway.

The snapshot ages. `captured_at` and `captured_unix` are published so a model
can notice that "fix this function" was said twenty minutes ago, and ask
rather than assume.

6. MAPPINGS                                                   *foyer-mappings*

All mappings below are buffer-local, created by the plugin, and currently not
configurable.

In the command buffer ~

A buffer with something to say already -- a lifted command line, a seeded
`command`, a prompt that is going to carry a `selection` -- starts in Insert
mode at the end of its text. One opened with nothing to say starts in Normal
mode, where <Up> walks history.

    <CR>              n    Send the buffer to the terminal
    <C-s>             i    Send the buffer to the terminal
    <C-p>, <Up>       n    Previous history entry
    <C-n>, <Down>     n    Next history entry
    <C-p>             i    Previous history entry
    <C-n>             i    Next history entry
                           (with a menu open, <C-p> and <C-n> move in it)
    @                 i    Mention an open file, see |foyer-mention|
    <C-x><C-p>        i    Ordinary insert-mode completion
    <C-x><C-n>        i    Ordinary insert-mode completion
    <Esc>             n    Close the window if the buffer is empty
    <C-c>             n    Close the window, discarding the draft
    <C-x><C-x>        n    Toggle previous size / full screen

History is stored per terminal name in `stdpath('cache')/foyer.json` and
survives restarts. Typing text before walking the history filters it to
entries containing that text, and highlights the match with |hl-FoyerMatch|.

                                                               *foyer-mention*
In the prompt for one of your `commands`, `@` at the start of a word lists the
open files: the one you opened the prompt from first, at your cursor line,
then the rest by when you last used them, each at its last change, then the
files you used recently (|v:oldfiles|) in the same way. The menu shows ten at
a time; typing after the `@` searches all of them by name, so a file further
down is found as you type. While it is open:

    <CR>       Put in `@src/parser.c:120`: the path as the agent resolves it,
               from the directory it was started in, or absolute for a
               `scope = 'global'` one.
    <C-l>      Put in the selection block a Visual selection sends, see
               |foyer-opts|: the file's last Visual selection if it holds the
               line, else the line alone.
    <Esc>      Leave the `@` as typed.

An `@` inside a word (`user@host`) is just an `@`, and so is one with no open
file to offer. The prompt of |foyer.edit_input()| has no mentions. A recent
file is read only when it comes into the menu, without its autocommands -- no
filetype plugin or language server starts for it -- and let go again when the
menu closes. A block put in with <C-l> is left out of history, which keeps the
words around it.

|foyer.edit_selection()|'s window is text you are editing rather than a
prompt: it keeps <CR>, <C-s>, <Esc>, <C-c> and <C-x><C-x>, has no history, and
always starts in Normal mode.

In the terminal buffer ~

The <C-x> mappings and the yank fix are on every terminal this plugin opens;
the rest are attached when a terminal is shown in one of this plugin's own
windows, which `switch` does not do -- it hands the terminal your window.

    [p                n    Jump to the previous shell prompt
    ]p                n    Jump to the next shell prompt
    <C-r>             n    cd to the project root, re-learn the prompt
    x                 n    Toggle previous size / full screen
    <CR>, <C-c>, <Esc> n   Close the terminal window
    <C-x>i            t    Paste register a at the prompt
    <C-x>w            t    Switch window, or tab if there is only one window
    <C-x>c            t    Close the terminal buffer

Yanking in a terminal buffer strips trailing whitespace from every line, since
a terminal pads its lines out to the window width.

7. HIGHLIGHTS                                               *foyer-highlights*

                                                               *hl-FoyerMatch*
FoyerMatch
    The filter text matched inside the history palette. Defaults to
    `bg=#333333 fg=#ff7700 bold`, declared with `default = true` so your
    colorscheme or an explicit |nvim_set_hl()| wins.

                                                            *hl-FoyerBackdrop*
FoyerBackdrop
    The veil dimming the editor while the |foyer.terminal_command()| picker
    is up, blended in at 'winblend' 40. Defaults to `bg=#000000`. Only drawn
    with 'termguicolors' set, since without it the veil cannot blend.

8. LIMITATIONS                                             *foyer-limitations*

- A send containing a newline -- a multi-line draft, or any prompt with a
  `selection` under it -- is wrapped in bracketed paste, so the
  receiver inserts the newline instead of reading it as Enter and running the
  first line on its own. What the receiver then does with a multi-line input
  is its own business: an agent takes it as one prompt, a shell lands it on
  one command line and still runs each of its lines in turn. A terminal
  program that does not understand bracketed paste shows the [200~ escapes as
  text -- set `bracketed_paste = false` for it, see |foyer-setup|. Single-line
  sends are never wrapped.
- |foyer.edit_selection()| goes through register a: the selection is yanked
  into it on the way in, and the edited text on the way back out. <C-x>i in a
  terminal pastes register a, whatever put it there.
- Reading the command line works by sending the erase sequence (CTRL-U, or ESC
  for cmd.exe, or whatever |foyer.send_prefix| names) and observing where the
  cursor lands, with short timers to let the shell respond. This is heuristic:
  an unusual prompt or a very slow shell can confuse it.
- Timings, mappings, and the register are hardcoded.
