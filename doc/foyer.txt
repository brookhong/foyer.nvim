1. INTRODUCTION                                           *foyer-introduction*

*foyer.nvim* puts a normal, modifiable buffer in front of a |terminal| buffer.
You compose a command with the full power of Vim, press <CR>, and the text is
sent to the shell.

A foyer is the room you pass through on the way in. Nothing reaches the shell
until you are done with it here.

It also manages named, project-scoped terminals, keeps a persistent per
terminal command history, and can edit a visual selection in a scratch window.

The plugin defines no global mappings. See |foyer-api| and wire up the
functions you want.

==============================================================================
2. REQUIREMENTS                                           *foyer-requirements*

Neovim 0.10 or newer. No other dependencies.

3. SETUP                                                         *foyer-setup*

                                                               *foyer.setup()*
setup({opts})

{opts} is a table with the following keys. All are optional.

commands ~
    Table of terminals, keyed by the single character that selects them in
    |foyer.terminal_command()|. Each value is one of:

    - a string: the command to run, e.g. `'zsh'`
    - a table `{ command, arguments }`; the first element doubles as the
      display name in the window title
    - a function `f(project_root, launch_info)` returning either of the above.
      It is called every time, so the terminal can depend on the project.

    A table entry may also name, alongside its two elements:

    cwd     Directory the terminal is spawned in, instead of the project root.
    scope   `'global'` keeps one terminal for the whole session, wherever you
            are. Anything else, or nothing, is the default: one terminal per
            project root. A global terminal's prompt takes the current window
            rather than a float or a sidebar, and the terminal takes it in
            turn once you send;
            closing either hands the window back to the buffer it showed.
            Use it for an agent you want a single long conversation with,
            apart from any project: >lua
        commands = {
            z = 'zsh',
            a = { 'opencode', '-c' },
            F = { 'opencode', '-c --agent counselor',
                  cwd = vim.env.HOME, scope = 'global' },
        }
<
root_markers ~
    List of directory markers used to locate the project root that scopes
    terminals, as accepted by |vim.fs.root()|. Defaults to
    `vim.g.root_markers`, then `{ '.git' }`.

bracketed_paste ~
    Whether a multi-line send is wrapped in bracketed paste, see
    |foyer-limitations|. Turn it off for a terminal program that does not
    understand the escapes. Defaults to `true`.

picker_delay ~
    Milliseconds |foyer.terminal_command()| waits for a terminal key before
    showing its picker. A key typed within it is taken with nothing drawn, so
    a mapping run straight through to the key does not flash the popup.
    Defaults to `500`.

selection_max_lines ~
    A selection is sent with its lines up to this many, and as its location
    alone beyond, see |foyer-opts|. `0` never sends the lines. Defaults to
    `40`. A buffer not yet written has no location to send instead, so a
    longer one is copied to a temporary file, which the label names.

mention ~
    Whether `@` in a terminal's prompt lists the open files to mention, see
    |foyer-mention|. Defaults to `true`.

keys ~
    The keys foyer maps in its own buffers, by action: `prompt` for the
    command buffer, `terminal` for a terminal foyer started, see
    |foyer-mappings| for what each does. Only the actions named change. An
    action takes a key or a list of keys, put in the modes it has by
    default; a table by mode, naming the modes itself; or `false`, for no
    key. A list replaces the default list rather than adding to it. Keys
    are read as each prompt or terminal is set up, so calling |foyer.setup()|
    again leaves the ones already open as they were. The defaults: >lua
        keys = {
            prompt = {
                send = { n = '<CR>', i = '<C-s>' },
                close = { n = '<C-c>' },
                close_if_empty = { n = '<Esc>' },
                terminal = { n = '<C-o>' },
                history_prev = { n = { '<Up>', '<C-p>' }, i = '<Up>' },
                history_next = { n = { '<Down>', '<C-n>' }, i = '<Down>' },
                history_pick = { n = '<C-f>', i = '<C-f>' },
            },
            terminal = {
                switch = { n = '<C-t>' },
                prompt = { n = '<C-o>' },
                close = { n = { '<CR>', '<C-c>', '<Esc>' } },
                cd_root = { n = '<C-r>' },
            },
        }
<

jump ~
    For |foyer.jump()|: `characters`, the keys its hint labels are made of
    (default `'asdfgqwertzxcvb'`), which also label the prompts
    |foyer-history| lists; `backdrop`, the 'winblend' of the backdrop
    dimming the editor behind it, or `false` for none (default `60`); and
    `fallback`, a function for a key that is no label (default: Telescope's
    oldfiles if installed, else |vim.ui.select()| over |v:oldfiles|).

Example: >lua
    require('foyer').setup({
        commands = {
            z = 'zsh',
            g = 'gdb',
            a = { 'opencode', '-c' },
        },
    })
<
                                                                  *foyer-opts*
                                                           *foyer.launch_info*
launch_info ~
    The context a prompt was composed with. |foyer.terminal_command()| and
    |foyer.send_terminal_command()| capture it
    themselves, so a mapping does no bookkeeping. Passing one explicitly
    overrides the capture. It reaches the `commands` resolver
    untouched -- the plugin never inspects it -- so a function there can pick
    the terminal by it. The shape is: >lua
        {
            project_root = '/repo',
            current_file = 'src/main.c',   -- relative to project_root
            current_line = 88,
            start_line = 30,  -- visual mode only, the lower line number
            end_line = 36,    -- visual mode only, the higher line number
        }
<
    `current_file` is named the way the project names it, not the way your
    filesystem does. The two keys always travel together: when there is no
    |foyer-setup| root to name the file against, `project_root` is absent and
    `current_file` is absolute instead.

    Any other key you add reaches the resolver too.

Command {opts} accepted by |foyer.terminal_command()| and
|foyer.send_terminal_command()|:

    command       Send this text instead of opening a command buffer.
    interactive   Force the command buffer open even when `command` is set;
                  `command` then seeds the buffer.
    selection     Text appended to the prompt as it is sent. Set for you
                  when the send starts in Visual mode. See below.
    win_type      `'sidebar'` for a right-hand split; otherwise floating.
                  Ignored for a `scope = 'global'` terminal, see
                  |foyer-setup|.
    auto_start    Spawn the terminal if it does not exist yet. The send
                  waits for it to start, see |foyer-limitations|.
    launch_info   See |foyer.launch_info|.

|foyer.terminal_command()| also accepts:

    key           The `commands` key to drive, instead of asking for one.
    switch        Show the terminal in the current window rather than opening
                  a prompt for it, and return its buffer.

Starting from Visual mode attaches the selection. The command buffer opens
empty and in Insert mode, with the selection's place shown in its title --
`src/main.c:30-36` -- and the selection joins below the prompt, after a blank
line, as it is sent: >
    what does this do?

    Selected in my editor: /repo/src/main.c, lines 30-36
    ```c
    ...the selected lines, as the buffer has them...
    ```
<
The lines go with it because a bare `src/main.c:30` reads to an agent as a
location, and it reads the lines around one and guesses which was meant; and
the numbers are the buffer's, while the agent reads the file on disk, which
unsaved edits can put out of step -- the label says so when they have. The
path is absolute, so it resolves wherever the agent was started. A selection
longer than `selection_max_lines` is sent as the label alone.

A buffer not yet written has no file to point at, so its lines are all the
agent gets: `Selected in my editor: lines 3-8 of a buffer with no file`, then
the lines, and `[No Name]:3-8` in the title. Past `selection_max_lines` a
label alone would point the agent at nothing, so the lines are copied to a
file under |tempname()| and the label names it -- `..., copied whole to
/tmp/.../3.lua` -- for the agent to read rather than a long paste for its input
box to swallow. The file is yours alone and goes when Neovim exits. A terminal
or scratch buffer ('buftype' set) sends no selection.

None of it sits in the command buffer, so the line stays yours to edit and to
walk history with, and history remembers the prompt without a selection that
will not be true next time. Type nothing and nothing is sent; a selection
alone asks the agent nothing. A `selection` you pass yourself is appended as
given.

A sidebar outlives the send that opened it, so sending again aims at the
window already there rather than splitting another one: a draft still in it is
yours and stays -- only an empty one takes a seeded `command` -- with the new
selection replacing whatever the title advertised before, and the terminal
left in there gives the window back to its prompt: empty after a send, still
holding the draft if you only looked at the terminal with <C-o>. A
floating window already open is reused the same way rather than stacked.
Launching a different terminal hands the sidebar or float to the new
terminal's prompt, in the same window; the previous terminal's prompt is set
aside with its draft, and comes back as you left it when that terminal is
launched there again.

A terminal still producing output keeps the window instead, see
|foyer.is_idle()|; there is no prompt for a selection to ride on then, so it
is dropped and said so via |vim.notify()|.

4. API                                                             *foyer-api*

                                                    *foyer.terminal_command()*
terminal_command({opts})
    Wait for a `commands` key, spawn that terminal if it is not running for
    the current project root, then open a command buffer for it. With no key
    typed within `picker_delay`, a popup lists the keys, tagging global
    terminals `global` and gathering them at the bottom, and marking running
    ones `●`. <Esc> or CTRL-C cancels; a key that names no terminal is
    ignored, and one typed before the popup showed brings it up.

    `opts.key` names the terminal outright, so a mapping can go straight to
    one, and `opts.switch` steps into its buffer instead of opening a prompt.
    A `scope = 'global'` terminal opens its prompt in the current window: >lua
        vim.keymap.set({ 'n', 'v' }, '<leader>af', function()
            foyer.terminal_command({ key = 'F' })
        end, { desc = 'opencode terminal' })
<
                                               *foyer.send_terminal_command()*
send_terminal_command({term_key}, {opts})
    Drive a specific terminal without prompting for a character. With
    `opts.command` set, the text is sent non-interactively; otherwise a
    command buffer opens. With `opts.auto_start` the terminal is created if it
    is missing.

                                                     *foyer.switch_terminal()*
switch_terminal()
    Switch to this project's running terminal used last before the current
    one, as CTRL-^ does for buffers: with two it toggles. A terminal counts
    as used when it is launched, shown, or its prompt is entered. Global
    terminals are left out, and none is started. The other terminal is shown
    in the same window; in the sidebar or float foyer keeps, its prompt is a
    <C-o> away with the draft left in it, and the terminal left keeps its
    own. In any other window the terminal is just shown there. Mapped to
    `keys.terminal.switch` in foyer's terminals.

                                                      *foyer.edit_selection()*
edit_selection()
    Open the current visual selection in a floating buffer and replace the
    selection with the result. Must be called from Visual mode. Uses register
    a as the transport.

                                                    *foyer.toggle_full_size()*
toggle_full_size()
    Toggle the current window between full screen and the size it had before:
    height for a float; for a split, width and height both, so it fills the
    screen whether it was split beside its neighbours, above or below them, or
    in a layout of both, as CTRL-W | and CTRL-W _ together would. Putting it
    back restores every split in the tab page to the size it had; floats,
    which take no room from anyone, are left as they are. If splits have come
    or gone since, that no longer fits them, and only the window's own width
    and height go back, each only where a neighbour is left to take it from.
    The size is remembered per window. Full screen is a request, not a
    promise: a neighbouring split keeps its minimum size, so a split may stop
    a few columns or lines short.

    No key is mapped to it: map one of your own, for every window, foyer's
    prompts and terminals among them: >lua
        vim.keymap.set('n', '<leader>z', require('foyer').toggle_full_size)
<

                                                                *foyer.jump()*
jump()
    Jump to any tab, window, buffer or recently opened file by typing the hint
    label drawn over it, after the tab switcher of Surfingkeys. Every tab page
    is laid out with its windows placed as on screen, then the listed buffers
    no window shows, by when they were last used, then recent files, each
    name just long enough to tell it from the others. Type a label to go
    there: to a window, or to a buffer or file opened in this one. With Shift
    a label does the other thing: a window's buffer comes into this window,
    and a buffer or file opens in a new tab. An empty window a buffer is
    brought into leaves no `[No Name]` behind. <BS> starts the label again,
    <Esc> cancels, any other key hands over to `jump.fallback`, see
    |foyer-setup|. A window squeezed flat by a full-screen neighbour is left
    out, as |foyer.tab_switch()| does; what it shows is still listed among the
    buffers. The terminals foyer started are not listed:
    |foyer.terminal_command()| reaches this project's and the global ones, in
    a window with the prompt a <C-o> away, and another project's is reached
    from that project. One shown in a window is still listed under Windows,
    and a terminal you opened yourself is listed as any buffer.

    It opens in a bordered window titled "Jump / Foyer", with the keys along
    its bottom edge, and fits it whatever it holds. Tabs too many to sit side
    by side carry on in bands below, each under a line of `─`. A name that
    needs many directories to tell it apart, as copies of a project on two
    drives do, keeps only the one that does and the last two:
    `C:/…/module/init.lua` and `D:/…/module/init.lua`. A name still too long
    for the window loses its start to `…`, keeping the file name. >lua
        vim.keymap.set('n', '<leader>b', require('foyer').jump)
<

                                                          *foyer.tab_switch()*
tab_switch()
    Move to the next window worth looking at: CTRL-W w order, wrapping around,
    skipping floats and any window a full-screen neighbour has squeezed down to
    'winminwidth' or 'winminheight'. With one window on top and two below whose
    left pane is squeezed, the right-hand pane therefore switches to the top
    window.

    When nothing is left to step into, the window stays put and the buffer
    changes instead, like CTRL-^. That happens when the tab page holds no other
    window — a float over it is not a destination — and when every other window
    is squeezed flat.

    A diff is the exception: a diff pane maximised with
    |foyer.toggle_full_size()| gives the squeezed pane its size back and steps
    into it, because a diff only reads beside its other half.

                                                              *foyer.is_idle()*
is_idle({buf}, {threshold_ms})
    Return true when {buf} has produced no output for {threshold_ms}
    milliseconds (default 1000). Used internally to decide whether a terminal
    is still busy, in which case the terminal is shown instead of a new
    command buffer.

==============================================================================
5. AGENT CONTEXT                                               *foyer-context*

Everything foyer tells an agent about your editor is in the prompt itself. A
Visual selection rides along below what you wrote, labelled with its file and
lines, see |foyer-opts|; `@` puts in a file at a line, the one you opened the
prompt from first, at your cursor, see |foyer-mention|. "Fix this" and `@<CR>`
make `fix this @src/main.c:88`, which every agent understands as it is.

==============================================================================
6. MAPPINGS                                                   *foyer-mappings*

All mappings below are buffer-local and created by the plugin. Each is set
by the `keys` action named beside it, see |foyer-setup|; the `@` menu's are
not configurable. |foyer.edit_selection()|'s window takes `send`, `close`
and `close_if_empty` from `keys.prompt`.

In the command buffer ~

A buffer with something to say already -- a seeded `command`, a prompt that
is going to carry a `selection` -- starts in Insert mode at the end of its
text. One opened with nothing to say starts in Normal mode, where <Up> walks
history.

    <CR>              n    Send the buffer to the terminal (`send`)
    <C-s>             i    Send the buffer to the terminal (`send`)
    <C-p>, <Up>       n    Previous history entry (`history_prev`)
    <C-n>, <Down>     n    Next history entry (`history_next`)
    <Up>              i    Previous history entry, from the first line
                           (`history_prev`)
    <Down>            i    Next history entry, from the last line
                           (`history_next`)
                           (elsewhere in a draft of many lines, or with a
                           menu open, the keys' own)
    <C-f>             n i  Label the most used prompts: a label inserts
                           one at the cursor, Shift+label replaces the
                           draft with it; `/` filters them; with a
                           menu open, the menu's (`history_pick`)
    @                 i    Mention an open file, see |foyer-mention|
    <Esc>             n    Close the window if the buffer is empty
                           (`close_if_empty`)
    <C-c>             n    Close the window, discarding the draft (`close`)
    <C-o>             n    Show the prompt's terminal in its window
                           (`terminal`)

Once a prompt is sent, the terminal takes its window, and <C-o> from there
comes back to the prompt emptied, with the selection it carried gone: a
follow-up written there goes alone. What was sent is in history, one <Up>
away. <C-o> works before a send too: from the prompt it shows the terminal,
to read what it has said, and <C-o> there brings back the draft as it was
left. It only ever toggles between the two, never to the file the prompt was
opened from; Insert-mode |i_CTRL-O| is Vim's own.

History is stored per terminal name in `stdpath('cache')/foyer.json` and
survives restarts. Typing text before walking the history filters it to
entries containing that text, and highlights the match with |hl-FoyerMatch|.

                                                               *foyer-history*
In Insert mode <C-p> and <C-n> are completion's, as anywhere else, and
<Up>/<Down> walk history as a shell's do: in a draft of many lines they move
the cursor until it is on the first line, or the last, and only from there
recall an entry. A walk under way goes on wherever the cursor is, so an entry
of many lines is stepped over in one press.

<Up> walks history by recency. <C-f> lists it by how often and how recently
each prompt was sent: its number of uses, halved for every week since the
last, in a popup just below the cursor, or above it with no room below.
Each is wrapped to the prompt's width, up to four rows, blank lines left out,
and gets a hint label, as in |foyer.jump()|, made of `jump.characters`, one
prompt per character. A label puts its prompt in at the cursor, after it in
Normal mode as |p| does, at it in Insert mode as typing does, and leaves the
cursor past it; the label with Shift replaces the whole draft with it. Nothing
is sent until you send it. The list is not filtered by the draft, so the draft
never changes which prompt is behind which label. The key is
`keys.prompt.history_pick`, see |foyer-setup|.

`/` in the list filters it: what you type narrows it as you go to the
prompts holding every word of it, in any order, ignoring the case of A to Z
-- `stage review` finds "review the staged changes" -- over the whole
history rather than the prompts on screen, still the most worth recalling
first, the words highlighted with |hl-FoyerMatch|. What you type shows in the
list's top border, and the list keeps the size and place it opened with, so
nothing moves as it narrows. <BS> takes a character back, <C-w> a word, <C-u>
the lot. <CR> goes back to picking, the labels given out afresh to what is
left; <Esc> clears the filter, and once there is none closes the list.

                                                               *foyer-mention*
In the prompt for one of your `commands`, `@` at the start of a word lists the
open files: the one you opened the prompt from first, at your cursor line,
then the rest by when you last used them, each at its last change, then the
files you used recently (|v:oldfiles|) in the same way. The menu shows ten at
a time; typing after the `@` searches all of them by name, so a file further
down is found as you type. While it is open:

    <CR>       Put in `@src/parser.c:120`: the path as the agent resolves it,
               from the directory it was started in, or absolute for a
               `scope = 'global'` one.
    <C-l>      Put in the selection block a Visual selection sends, see
               |foyer-opts|: the file's last Visual selection if it holds the
               line, else the line alone.
    <Esc>      Leave the `@` as typed.

An `@` inside a word (`user@host`) is just an `@`, and so is one with no open
file to offer. A recent file is read only when it comes into the menu,
without its autocommands -- no filetype plugin or language server starts for
it -- and let go again when the menu closes. A block put in with <C-l> is left
out of history, which keeps the words around it.

|foyer.edit_selection()|'s window is text you are editing rather than a
prompt: it keeps <CR>, <C-s>, <Esc> and <C-c>, has no history, and always
starts in Normal mode. With no terminal behind it, <C-o> there does nothing.

In the terminal buffer ~

<C-t> and the yank fix are on every terminal this plugin opens; the rest are
attached when a terminal is shown in one of this plugin's own windows, which
`switch` does not do -- it hands the terminal your window. None is mapped in
Terminal mode, where every key is the program's. In `keys.terminal`:

    <C-t>             n    |foyer.switch_terminal()| (`switch`)
    <C-r>             n    cd to the project root (`cd_root`)
    <C-o>             n    Back to the prompt the terminal was shown for
                           in this window; in one of yours, the key's own
                           meaning, Vim's |CTRL-O| (`prompt`)
    <CR>, <C-c>, <Esc> n   Close the terminal window (`close`)

Yanking in a terminal buffer strips trailing whitespace from every line, since
a terminal pads its lines out to the window width.

A terminal follows its output in every window showing it, once foyer has shown
it or sent it something: the cursor goes to the last line, so what comes after
stays in view without Terminal mode. Move the cursor up to read back, and the
window stays put until the next send.

7. HIGHLIGHTS                                               *foyer-highlights*

                                                               *hl-FoyerMatch*
FoyerMatch
    What the draft matches as <Up> walks history, and the words a `/` filter
    matches in the <C-f> list, see |foyer-history|. Defaults to
    `bg=#333333 fg=#ff7700 bold`, declared with `default = true` so your
    colorscheme or an explicit |nvim_set_hl()| wins.

                                                            *hl-FoyerBackdrop*
FoyerBackdrop
    The veil dimming the editor while the |foyer.terminal_command()| picker
    is up, blended in at 'winblend' 40. Defaults to `bg=#000000`. Only drawn
    with 'termguicolors' set, since without it the veil cannot blend.

|foyer.jump()| has its own, with a palette for each 'background', given as
colors rather than links so they stay distinct in any colorscheme. Groups you
set yourself are kept; set them from a |ColorScheme| autocmd, since a
colorscheme change clears them.

    FoyerJumpTitle          section titles
    FoyerJumpName           buffer, window and file names
    FoyerJumpCurrent        the current buffer or window
    FoyerJumpNoName         buffers without a file name
    FoyerJumpTerminal       terminals foyer started
    FoyerJumpLabel          hint labels
    FoyerJumpLabelTyped     the part of a hint label already typed
    FoyerJumpBackdrop       dims the editor behind it, see `jump.backdrop`

8. LIMITATIONS                                             *foyer-limitations*

- A terminal foyer has just started gets nothing until it has: a program
  starting up has not taken over its terminal yet, and taking it over
  commonly throws away what was typed ahead. So a send to it -- an
  `auto_start` command, or a prompt written faster than the agent came up --
  is held, with a notice, until the program has drawn its first screen and
  been quiet for half a second, and then sent. One that draws nothing is
  taken as started after three seconds; one that never settles is sent to
  after fifteen, with a warning. Prompts open at once either way, so the
  writing does not wait.
- Its first prompt is also typed without Enter, and the Enter goes only once
  the text has shown on its screen. A program can come up on a question of
  its own -- whether to trust the workspace, a login, an update -- and there
  the Enter that ends a prompt would be the answer, given for you. So if the
  text has not shown within two seconds, foyer sends nothing more and says
  so: the question is yours to answer in the terminal, and the prompt is in
  history, one <Up> away, to send again afterwards. While it waits, foyer
  keeps out of Terminal mode, so no key of yours reaches the question by
  accident.
- A send containing a newline -- a multi-line draft, or any prompt with a
  `selection` under it -- is wrapped in bracketed paste, so the
  receiver inserts the newline instead of reading it as Enter and running the
  first line on its own. What the receiver then does with a multi-line input
  is its own business: an agent takes it as one prompt, a shell lands it on
  one command line and still runs each of its lines in turn. A terminal
  program that does not understand bracketed paste shows the [200~ escapes as
  text -- set `bracketed_paste = false` for it, see |foyer-setup|. Single-line
  sends are never wrapped.
- |foyer.edit_selection()| goes through register a: the selection is yanked
  into it on the way in, and the edited text on the way back out.
- Timings and the register are hardcoded.
