1. INTRODUCTION                                           *foyer-introduction*

*foyer.nvim* puts a normal, modifiable buffer in front of a |terminal| buffer.
You compose a command with the full power of Vim, press <CR>, and the text is
sent to the shell.

A foyer is the room you pass through on the way in. Nothing reaches the shell
until you are done with it here.

It also manages named, project-scoped terminals, keeps a persistent per
terminal command history, and can edit a visual selection in a scratch window.

The plugin defines no global mappings. See |foyer-api| and wire up the
functions you want.

==============================================================================
2. REQUIREMENTS                                           *foyer-requirements*

Neovim 0.10 or newer. No other dependencies.

3. SETUP                                                         *foyer-setup*

                                                               *foyer.setup()*
setup({opts})

{opts} is a table with the following keys. All are optional.

commands ~
    Table of terminals, keyed by the single character that selects them in
    |foyer.terminal_command()|. Each value is one of:

    - a string: the command to run, e.g. `'zsh'`
    - a table `{ command, arguments }`; the first element doubles as the
      display name in the window title
    - a function `f(project_root, launch_info)` returning either of the above.
      It is called every time, so the terminal can depend on the project.

root_markers ~
    List of directory markers used to locate the project root that scopes
    terminals, as accepted by |vim.fs.root()|. Defaults to
    `vim.g.root_markers`, then `{ '.git' }`.

Example: >lua
    require('foyer').setup({
        commands = {
            z = 'zsh',
            g = 'gdb',
            a = { 'opencode', '-c' },
        },
    })
<
                                                                  *foyer-opts*
                                                           *foyer.launch_info*
launch_info ~
    The context a prompt was composed with. |foyer.terminal_command()|,
    |foyer.send_terminal_command()| and |foyer.open_terminal()| capture it
    themselves, so a mapping does no bookkeeping. Passing one explicitly
    overrides the capture. It reaches the `commands` resolver
    untouched -- the plugin never inspects it -- and is published per terminal
    for an agent to read later, see |foyer-context|. The shape is: >lua
        {
            current_file = vim.fn.expand('%:p'),
            current_line = vim.fn.line('.'),
            start_line = vim.fn.line('v'),   -- visual mode only
            end_line = vim.fn.line('.'),     -- visual mode only
        }
<
    Any other key you add travels with it, all the way to the agent.

Command {opts} accepted by |foyer.terminal_command()| and
|foyer.send_terminal_command()|:

    command       Send this text instead of opening a command buffer.
    interactive   Force the command buffer open even when `command` is set.
    selection     `'@'` seeds the command buffer from register a. Set for you
                  when the send starts in Visual mode.
    win_type      `'sidebar'` for a right-hand split; otherwise floating.
    auto_start    Spawn the terminal if it does not exist yet.
    launch_info   See |foyer.launch_info|.

4. API                                                             *foyer-api*

                                                    *foyer.terminal_command()*
terminal_command({opts})
    Read one character, resolve it against `commands`, spawn that terminal if
    it is not running for the current project root, then open a command buffer
    for it. An unknown character lists the available terminals via
    |vim.notify()|.

                                               *foyer.send_terminal_command()*
send_terminal_command({term_key}, {opts})
    Drive a specific terminal without prompting for a character. With
    `opts.command` set, the text is sent non-interactively; otherwise a
    command buffer opens. With `opts.auto_start` the terminal is created if it
    is missing.

                                                          *foyer.edit_input()*
edit_input()
    Lift the terminal's current, half-typed command line into a floating
    buffer and write the edited result back to the prompt. Must be called from
    a terminal buffer, in Normal mode.

                                                      *foyer.edit_selection()*
edit_selection()
    Open the current visual selection in a floating buffer and replace the
    selection with the result. Must be called from Visual mode. Uses register
    a as the transport.

                                                    *foyer.toggle_full_size()*
toggle_full_size()
    Toggle the current window between full screen and the size it had before:
    height for a float, width for a split. The size is remembered per window,
    so two windows toggle independently. Full screen is a request, not a
    promise: a neighbouring split keeps its minimum width, so a split may stop
    a few columns short of 'columns'.

                                                          *foyer.tab_switch()*
tab_switch()
    Move to the next window worth looking at: CTRL-W w order, wrapping around,
    skipping floats and any window a full-screen neighbour has squeezed down to
    'winminwidth' or 'winminheight'. With one window on top and two below whose
    left pane is squeezed, the right-hand pane therefore switches to the top
    window.

    When nothing is left to step into, the window stays put and the buffer
    changes instead, like CTRL-^. That happens when the tab page holds no other
    window — a float over it is not a destination — and when every other window
    is squeezed flat.

    A diff is the exception: a diff pane maximised with
    |foyer.toggle_full_size()| gives the squeezed pane its size back and steps
    into it, because a diff only reads beside its other half.

                                                             *foyer.is_idle()*
is_idle({buf}, {threshold_ms})
    Return true when {buf} has produced no output for {threshold_ms}
    milliseconds (default 1000). Used internally to decide whether a terminal
    is still busy, in which case the terminal is shown instead of a new
    command buffer.

                                                       *foyer.open_terminal()*
open_terminal({name}, {command}, {opts})
    Open, or switch to, a terminal that is not scoped to a project: one reused
    buffer per {name}, spawned in `opts.cwd` (default $HOME). Use it for an
    agent you want one long conversation with wherever you are; the `commands`
    terminals of |foyer.setup()| are keyed by project root instead.

    {name} keys both the reused buffer and the context file, so keep it short.
    {opts} may carry `cwd` and `launch_info`; the context is published on
    every call, switch or spawn, so an agent already running in there learns
    where you are now. Returns the terminal buffer.
>lua
        vim.keymap.set({ 'n', 'v' }, '<leader>af', function()
            foyer.open_terminal('opencode', 'opencode -c')
        end, { desc = 'Home opencode terminal' })
<
    The context and the terminal-buffer mappings are handled for you; a
    terminal spawned by hand gets neither. Note that this does not open one of
    this plugin's own windows, so only the <C-x> mappings are attached, see
    |foyer-mappings|.

5. AGENT CONTEXT                                               *foyer-context*

On every send, the |foyer.launch_info| attached to it is written as JSON to a
file per terminal, and every terminal this plugin spawns has $FOYER_CONTEXT in
its environment naming that file: >console

    $ cat "$FOYER_CONTEXT"
    {"captured_at":"2026-09-22T15:59:07+0800","captured_unix":1790063947,
     "launch_info":{"current_file":"/repo/src/main.c","current_line":88,
                    "start_line":30,"end_line":36}}
<
That is the whole interface -- a file an agent reads when it needs it. What
remains is telling the agent it is there.

`skills/foyer-editor-context/SKILL.md` in this repository does that as an
agent skill: only its one-line description sits in the model's context, and
the body is loaded on demand, when a request actually points at the editor.
Symlink it into whichever skill directory your CLI scans --
`~/.config/opencode/skills/`, `~/.kiro/skills/`, `~/.claude/skills/` --
keeping the directory name: >

    mkdir -p ~/.config/opencode/skills/foyer-editor-context
    ln -sf /path/to/foyer.nvim/skills/foyer-editor-context/SKILL.md \
        ~/.config/opencode/skills/foyer-editor-context/SKILL.md
<
A CLI with no skill mechanism can carry the same thing as an always-loaded
rule (`AGENTS.md`, `CLAUDE.md`, `~/.kiro/steering/*.md`), at the cost of those
tokens on every request: >

    When $FOYER_CONTEXT is set it names a JSON file holding the file, line
    and selection the user had when they wrote their prompt. Read it with
    `cat "$FOYER_CONTEXT"` before acting on "this file", "here", "this line"
    or "my selection". If it is unset, ask which file is meant.
<
Each terminal has its own file, so an agent in one project never reads a path
attached for another. |foyer.open_terminal()| covers terminals outside the
project-scoped `commands`; one opened by hand has neither the variable nor a
send to trigger a publish, and its agent has nothing to read.

The files live in `stdpath('cache')/foyer/`, one per terminal, and are removed
on |VimLeavePre|. A terminal closed and reopened keeps its file, so a long
session does not litter the directory.

Publishing never takes a send down with it. A `launch_info` holding something
|vim.json.encode()| refuses, or a cache directory that cannot be written,
warns and the command is sent anyway.

The snapshot ages. `captured_at` and `captured_unix` are published so a model
can notice that "fix this function" was said twenty minutes ago, and ask
rather than assume.

6. MAPPINGS                                                   *foyer-mappings*

All mappings below are buffer-local, created by the plugin, and currently not
configurable.

In the command buffer ~

    <CR>              n    Send the buffer to the terminal
    <C-s>             i    Send the buffer to the terminal
    <C-p>, <Up>       n i  Previous history entry, filtered by what you typed
    <C-n>, <Down>     n i  Next history entry
    <C-x><C-p>        i    Ordinary insert-mode completion
    <C-x><C-n>        i    Ordinary insert-mode completion
    <Esc>             n    Close the window if the buffer is empty
    <C-c>             n    Close the window, discarding the draft
    <C-x><C-x>        n    Toggle previous size / full screen

History is stored per terminal name in `stdpath('cache')/foyer.json` and
survives restarts. Typing text before pressing <C-p> filters the history to
entries containing it, and highlights the match with |hl-FoyerMatch|.

In the terminal buffer ~

The <C-x> mappings and the yank fix are on every terminal this plugin opens;
the rest are attached when a terminal is shown in one of this plugin's own
windows, which |foyer.open_terminal()| does not do.

    [p                n    Jump to the previous shell prompt
    ]p                n    Jump to the next shell prompt
    <C-r>             n    cd to the project root, re-learn the prompt
    x                 n    Toggle previous size / full screen
    <CR>, <C-c>, <Esc> n   Close the terminal window
    <C-x>i            t    Paste register a at the prompt
    <C-x>w            t    Switch window, or tab if there is only one window
    <C-x>c            t    Close the terminal buffer

Yanking in a terminal buffer strips trailing whitespace from every line, since
a terminal pads its lines out to the window width.

7. HIGHLIGHTS                                               *foyer-highlights*

                                                               *hl-FoyerMatch*
FoyerMatch
    The filter text matched inside the history palette. Defaults to
    `bg=#333333 fg=#ff7700 bold`, declared with `default = true` so your
    colorscheme or an explicit |nvim_set_hl()| wins.

==============================================================================
8. LIMITATIONS                                             *foyer-limitations*

- Register a is the transport for selections and pastes: a send from Visual
  mode yanks into it, and a command buffer seeded from it consumes and clears
  it. |foyer.edit_selection()| does the same.
- Reading the command line works by sending an erase sequence (CTRL-U, or ESC
  for cmd.exe) and observing where the cursor lands, with short timers to let
  the shell respond. This is heuristic: an unusual prompt or a very slow shell
  can confuse it.
- Timings, mappings, and the register are hardcoded.
